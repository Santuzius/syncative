# Testing

**Never test with a real instance.** Its accounts, keyring entries, database (`~/.local/share/syncative`), config (`~/.config/syncative`) and `$XDG_RUNTIME_DIR/syncative/rclone.conf` sync real data; a test sharing any of them can overwrite tokens or start syncs and deletions. Test only with throwaway accounts or mock remotes, in an isolated instance.

Keep test loops fast: poll every ≈0.5 s and stop as soon as the condition holds, with tight timeouts instead of fixed `sleep 20`. Start a pass with *Sync now* instead of waiting for the interval.

## Desktop
`scripts/test-instance.sh` starts an isolated instance: its own HOME and XDG folders under `/tmp/syncative-test`, its own D-Bus session with its own gnome-keyring, and no Wayland socket. It refuses to start if something else owns the keyring service.

- `scripts/test-instance.sh xvfb` runs headless on display `:99`; `scripts/test-instance.sh desktop` shows the window on the desktop, e.g. to sign in throwaway accounts. Add `--release` for the release build.
- `scripts/test-screenshot.sh` takes screenshots into `temp/` and sends clicks, text and keys to the headless window.
- `scripts/test-seed-mock.sh` adds offline mock remotes: a real two-way sync between two local folders, an unreachable WebDAV remote (error state) and a Proton remote without a session ("Not signed in").
- **Storage line:** LocalMock (an `alias` onto a local dir) answers rclone's `about` with the statfs numbers of that directory's disk, so the storage line in the remote page's header shows offline; OfflineMock (dead port) and ProtonMock (no session) report nothing and show no line.
- `scripts/test-mem.sh` prints the memory use of the test instance.
- Variables: `SYNCATIVE_TEST_RESET=1` wipes the test state, `SYNCATIVE_TEST_BIN` runs another build, `SYNCATIVE_TEST_SHOW=0` starts in the tray, `SYNCATIVE_COLOR_SCHEME=light|dark` forces the theme.
- **The test instance's remotes from the command line:** its `rclone.conf` is encrypted with a password in its keyring. Read it through the instance's D-Bus session (`DBUS_SESSION_BUS_ADDRESS` from `/proc/<pid>/environ` of the running test Syncative): `secret-tool lookup service "Syncative Keys" username rclone-config-password`, then `RCLONE_CONFIG_PASS=… rclone --config /tmp/syncative-test/run/syncative/rclone.conf md5sum GoogleDrive:<folder>`.
- **A file saved while it uploads:** a sync folder with a 5 MB file that a loop replaces every 2 s (write a temporary file, then `mv` over it, as editors do) for about 45 s; afterwards the remote must hold the last version, and the log (with *Detailed log* on, the file `detailed-log` in the data folder) must show no `corrupted on transfer`. Larger files only work on a fast connection.
- **Metered networks:** `SYNCATIVE_TEST_PORTAL=1 scripts/test-instance.sh xvfb` gives the instance a fake portal network monitor (`scripts/fake-network-portal.py`), which reports a metered network while `/tmp/syncative-test/metered` exists and signals each change; the log then says `network metered` or `network unmetered`.
- **Nextcloud:** a beta feature (Preferences → Beta features), tested against a local Nextcloud in Docker: the official `nextcloud` image with MariaDB, on `http://localhost:8082` with its own test user. After about ten failed sign-ins from one address, Nextcloud answers every request from it with `429 Too Many Requests`, the right password included, until `occ security:bruteforce:reset <address>` (the Docker gateway). The space it reports lags a few seconds behind uploads, and a quota set with `occ user:setting <user> files quota` shows only after the next upload.
- **Remote change detection:** a sync folder's change cursor sits in `sync_dirs.remote_cursor`, set only by a pass whose remote side matched `sync_items` (see `src/services/sync/remote_view.rs`); while it is set, a pass without remote changes lists nothing. With *Detailed log* on, a pass that applied changes logs `applied N remote change(s) instead of listing`, and a full listing by a backend with a change source logs `lists the remote folder:` with the reason. On Nextcloud, `docker logs nextcloud` shows one `PROPFIND` of the remote's root per quiet pass, whatever the number of sync folders; a change adds one per sync folder and the walk one per changed subfolder. The Go tests of `src/go/rclone` check the ETags and the shared connection against a server given by `SYNCATIVE_NEXTCLOUD_URL`, `SYNCATIVE_NEXTCLOUD_USER` and `SYNCATIVE_NEXTCLOUD_PASS` (`TestFolderTagsOnNextcloud`). To force a listing, clear the column (`update sync_dirs set remote_cursor = null`) while the instance is stopped. The [remote checklist](#checklist-for-a-remote) tests the change paths.
- **Dead connections (hibernate, network change):** rclone and Proton notice a dead HTTP/2 connection by its unanswered pings (`src/go/nethealth`, whose Go tests freeze a connection and send a slow reply). By hand: put a TLS proxy such as `caddy reverse-proxy` in front of the local Nextcloud, trust its root certificate in the test instance with `SSL_CERT_FILE`, and add a TCP proxy in between that can stop passing data on its open connections. Frozen, the listing must fail with `http2: client connection lost` after about 30 s and the next sync dial anew; `docker pause nextcloud` for a minute (a slow server) must not fail anything. `GODEBUG=http2debug=1` shows whether rclone speaks HTTP/2 at all.
- **Network loss:** start the instance with `HTTPS_PROXY`/`HTTP_PROXY` pointing at a local CONNECT proxy and kill the proxy, or point them at a dead port such as `127.0.0.1:9`. Rclone and Proton both go through it. Stopping the proxy with `kill -STOP` freezes every connection (a dead connection); killing it then and starting a new one stands in for a new network. Upload a file of 150 MB to have a pass running when the connection goes.

- **File manager context menu:** "Context menu in the file manager" in Preferences, a beta feature, writes the service menu into the instance's own home, where the real Dolphin doesn't look. To try it from the real Dolphin with the test instance, use a service menu whose `Exec` is `scripts/test-save.sh %F`; the script hands the files to the running test instance and refuses when none runs, as the launch would otherwise start a Syncative of its own. `scripts/test-save.sh FILE…` does the same from a terminal.

## Checklist for a remote
Run it for every new remote type, for beta remotes such as Nextcloud before they leave the beta, and after larger changes to a remote's listing, caching or change detection.

**Setup:** a throwaway account, signed in to the desktop test instance and to a second client of the same account: the provider's web app, and where possible Syncative on the phone. Sync at least two folders: a new one and one that already existed on the remote with content (created by another client, not by Syncative). Turn *Detailed log* on. A person doing the steps in the web app works step by step with whoever watches the logs: one change, *Sync now*, check, next change.

For Google Drive, rclone with the test instance's config (see above) can stand in for the web app while the phone syncs: `moveto` renames and moves, `deletefile` and `purge` move to the trash, and `backend untrash GoogleDrive:<folder>` restores everything in the trash below that folder, earlier test leftovers included. It doesn't restore a trashed folder itself (step 6): the Drive API does, `PATCH https://www.googleapis.com/drive/v3/files/<id>` with `{"trashed":false}`, the ID from `lsjson --drive-trashed-only` and the access token from `config dump`.

For Proton, `src/go/cmd/protonctl` does the same through a saved session: `go build -o temp/protonctl ./cmd/protonctl` in `src/go`, then `protonctl SESSION ls|tree|put|mkdir|trash|mv|restore` (`mv` renames and moves, `restore` takes an item out of the trash). SESSION is a JSON file with the test instance's session, from `secret-tool lookup service "Syncative Keys" username proton-session-<remote>` (see above), read while the instance runs and used only after it stopped, since a token rotation by one signs the other out. Stop the instance, make the changes, start it again: that also covers step 7.

After each step the local folder and the remote must match, and a second pass must change nothing (no endless uploads, downloads or "Checking for changes" loops).

1. **Own changes:** add, change and delete files and a subfolder locally.
2. **Changes by another client** (web app or phone): a new, a changed and a deleted file; a new subfolder with files.
3. **Renames and moves** in the web app: rename a file and a folder with content; move a file and a folder between two sync folders and within one; move a folder out of every sync folder and back in.
4. **Trash and restore** a file and a folder with content.
5. **Time only:** a file whose content stays the same but whose modification time changes (touch it locally; on the remote, upload the same content again) settles after one pass.
6. **The sync folder's own remote folder** renamed, then trashed: the folder shows the error state "Remote folder not found", nothing is deleted locally; after the rename back or the restore it syncs again by itself.
7. **Restart:** stop and start the instance between changes; changes made while it was stopped arrive. For a remote with a cache on disk, also a damaged or deleted cache file (it lists again) and a cache older than the provider keeps its change log.
8. **Removing the remote** deletes everything Syncative kept for it (session, cache files), and nothing on the remote or locally.
9. **Errors:** network loss in the middle of a pass and a dead connection (see above); the next pass recovers without deleting anything.

## Ubuntu VM
`temp/vm/start.sh` (not committed) starts an Ubuntu 24.04 VM with KDE Plasma headless: SSH on `localhost:2222` with `temp/vm/vmkey` as user `tester`, screenshots through `screendump` on the QEMU monitor socket `temp/vm/monitor.sock`. Nautilus and Nemo are installed there too.

- **A build for it:** an AppImage. `scripts/build-appimage.sh` writes to `temp/release/` and would replace a released AppImage of the same version, whose hash Nix pins; for tests, run a copy with another output folder.
- **Network:** netplan sets up the network through systemd-networkd, so NetworkManager reports no connection, the portal says the same and Syncative stays Offline. `sudo systemctl stop NetworkManager` and `systemctl --user restart xdg-desktop-portal` make the portal fall back to the default route. The session has no Secret Service, so Syncative keeps its rclone config unencrypted in `$XDG_RUNTIME_DIR/syncative/rclone.conf`, where a remote can be written directly.
- **Clicking:** the session is Wayland, where xdotool reaches no window. Started with `WAYLAND_DISPLAY` unset, `GDK_BACKEND=x11` and `QT_QPA_PLATFORM=xcb` (and `DISPLAY`, `XAUTHORITY` and `DBUS_SESSION_BUS_ADDRESS` taken from `plasmashell`'s environment), Syncative and the file managers run under XWayland, where xdotool works. Ubuntu's ydotool (0.1.8) moves only relative and drops events.
- An old AppImage starts there at login (autostart); stop it with `pkill -x syncative`. `pkill -f` with the AppImage's name also matches the SSH command that runs it.

## AppImage in containers
On a host with NixOS's `programs.appimage.binfmt`, the kernel hands every AppImage to `/run/binfmt/appimage_type_2`, which doesn't exist inside containers, so AppImages there fail with "No such file or directory", even with `--appimage-extract-and-run`. Unpack them with `unsquashfs -o <offset>` (the offset is the end of the ELF section header table) and run `squashfs-root/AppRun`. `appimage/Dockerfile` already blanks appimagetool's magic bytes for the build.

## Android
`scripts/android-dev.sh` builds the debug APK (with optimised native libraries), installs it on the USB phone and starts it. The debug variant lets `adb shell run-as io.github.santuzius.syncative` reach the app's files.

- **Build time:** about 1–2 minutes, so run the script in the foreground and wait for it to exit; it ends after the app was started or prints the first cargo errors. Don't put it in the background and poll it with `pgrep -f`: the pattern matches the polling shell itself, and the Gradle daemon keeps running for hours after a build. If Nix has to rebuild the Android SDK, e.g. on a new machine or after a nixpkgs update, the first build takes several minutes longer.
- **Offline remote:** run `rclone serve webdav /tmp/syncative-phone-webdav --addr 127.0.0.1:18080 --user test --pass test` on the PC and `adb reverse tcp:18080 tcp:18080`. Upload test files through WebDAV (`curl -T`), not straight into the folder, since `rclone serve` caches listings for 5 minutes.
- **Seeding the remote:** *Add remote* hides plain WebDAV (Nextcloud only with the beta features on), so add it through `run-as`: the rows in `files/syncative/data.sqlite`, the section in `files/run/syncative/rclone.conf` and a local folder such as `files/test-sync`. Syncative encrypts `rclone.conf` with rclone's config encryption and rewrites a plain-text file encrypted once at startup, so write the section while the app is stopped and before its config was encrypted, e.g. right after a fresh install.
- **Sharing to Syncative:** the share sheet of the Files app is the real path. From the PC, `am start -a android.intent.action.SEND -t text/plain --eu android.intent.extra.STREAM content://media/external/file/<id> -n io.github.santuzius.syncative/.SyncativeActivity` shares one file: push it to `/sdcard/Download`, have the media scanner pick it up (`am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file:///sdcard/Download/<name>`) and look up its `<id>` with `content query --uri content://media/external/file --projection _id --where "_display_name='<name>'"`. The copies sit in `cache/shared/` (`run-as`) until a folder is chosen, then in `files/syncative/uploads/` until they are up. A file of 150 MB keeps the upload going long enough to see the remote's state; `svc wifi disable` and `svc data disable` test the wait for the connection.
- **Engine without the window:** reinstalling the APK while Syncative runs sends `MY_PACKAGE_REPLACED` to `BootReceiver`, which starts `SyncService`. A force-stopped app gets no broadcasts until it is launched again.
- **Logs:** the phone's logcat buffer holds only a few minutes. For long background tests stream it to the PC (`adb logcat -v time > file &`) or read the database (`adb exec-out run-as … cat files/syncative/data.sqlite`, timestamps in `sync_items`). Never `pkill -f` a pattern that also matches your own command line.
- **GrapheneOS** behaves differently from stock Android in places: Storage Scopes and its own memory allocator (hardened_malloc).
- Uninstalling the app also removes the permissions granted to it (notifications, All files access).
- If others use the phone too, check the foreground app before sending taps.

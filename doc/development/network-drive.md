# Network drive

The fourth folder mode, *Network drive* 🧪 (`SyncMode::NetworkDrive`, a beta feature), syncs nothing. The folder's local path shows the remote folder through rclone's VFS, which downloads a file when it is opened and keeps recently used ones in its cache; changes are uploaded when a file is closed.

## Linux

- `src/go/mount_linux.go` links rclone's FUSE mount (`cmd/mount`), which registers rclone's remote-control calls `mount/mount` and `mount/unmount`. Rust sends them through the ordinary RPC call (`src/services/network_drive.rs`); no export of its own is needed.
- The mount uses `--vfs-cache-mode full`. The cache lies in rclone's default place, `~/.cache/rclone/vfs/<remote>/`.
- Users need `fusermount3` (the `fuse3` package). Without it the folder shows rclone's error and the hint to install it.
- **When it mounts:** a pass for the folder mounts it if this process hasn't yet, so it follows the remote's pause and the engine's schedule like any folder. Proton remotes work through Syncative's own rclone backend, Google Drive through rclone's.
- **When it unmounts:** when the folder or its remote is removed (the engine's reload, `network_drive::retain`) and when the app quits from the tray. Removing deletes the folder's VFS cache as well (`<cache>/vfs/<remote>/<path>` and `vfsMeta/…` in rclone's cache folder), on Android too; quitting keeps it. A Syncative that dies with a mount leaves a dead mount point ("Transport endpoint is not connected"); the next mount unmounts it lazily with `fusermount3 -u -z` first.
- **The folder must be empty** (or missing), as the mount hides what is in it. The add dialog refuses a folder with content.
- **File managers** list the mount by itself: GNOME Files and Nemo under Devices, with an eject button; Dolphin from KDE Frameworks 6.9 on, whose Solid counts `fuse.rclone` as a network share (Plasma 5 lists nothing). An eject unmounts the drive behind Syncative's back and rclone forgets it, so the next pass mounts it again (`mount/listmounts`): the folder stays a network drive until it is removed.
- **No switching:** a synced folder and a network drive hold different things locally (a full copy, or nothing), so the folder settings don't switch between them; the folder is removed and added again.

## Android

Apps have no FUSE on Android, so a document provider shows the folder instead: `NetworkDriveProvider.java` (authority `io.github.santuzius.syncative.networkdrive`), which the Files app and every app's Open and Save dialog list.

- **No local path:** the add dialog doesn't ask for one. The database keeps a stand-in, `/network-drive/<remote>/<remote path>` (`network_drive::android_path`), as it tells folders apart by their local path; the folder card says where to find the drive instead.
- **Roots:** each network drive folder is a root titled with the remote folder and the remote's name as summary (for the whole drive the remote's name as title and "Syncative" as summary). The engine hands the folders over when it reads them (`network_drive::publish`) and the provider's root list is told to refresh. A process that the provider started (no window, no sync service) starts the engine on the first root query, so the Files app first gets no roots and the drives a moment later.
- **Start of the process:** Android publishes a content provider before `Application.onCreate` runs, and its calls arrive on binder threads meanwhile; the provider waits for `SyncativeApplication` to have loaded the native library (`awaitNative`).
- **Go's environment:** the Go library takes its environment from the process start, before `SyncativeApplication` set `HOME`, `XDG_*` and `TMPDIR`, so rclone's cache would land in `/data/local/tmp`, which apps can't write. Rust hands the variables over at start (`syncative/environment`, `src/go/rclone/environment.go`).
- **Where it shows:** Android's own Files app and every Open and Save dialog. Files by Google lists Syncative under *Other storage*, but tapping it only starts the app (its launcher intent); it doesn't browse other apps' document providers.
- **The open button** of the folder card opens the drive's root URI in the app that shows folders (`Bridge.openNetworkDrive`); a document URI of another app's provider makes the Files app ask `findDocumentPath`, which the provider answers too.
- **Document IDs:** the folder's database ID, a slash and the path below it (`14/Photos/a.jpg`, `14` for the folder itself).
- **The VFS:** one per folder, by `remote:path`, with `--vfs-cache-mode full` like the Linux mount (`src/go/rclone/documents.go`). Its RPC calls `syncative/doc-*` list, stat, create, delete, rename, open and close; the bytes of an open file go through two exports of their own, `SyncativeDocRead` and `SyncativeDocWrite`. A pass "mounts" the folder by starting its VFS (`syncative/doc-attach`) and then polls it like a Linux mount.
- **Open files** are proxy file descriptors (`StorageManager.openProxyFileDescriptor`), each served by a thread of its own: Android waits for the size of a newly opened file while holding a lock of vold's, and a slow read of another file on a shared thread could keep it waiting until the watchdog restarts the system. Closing, which uploads a written file before it returns (write-back 0), runs off that thread for the same reason; a failed upload shows a notification. Both lessons come from [RSAF](https://github.com/chenxiaolong/RSAF), a document provider on rclone's VFS.
- **New files** are only listed (`AddVirtual`) until the app that created them writes and closes them; the upload then happens once instead of an empty file first.
- **Slow listings:** a listing not done within half a second answers "loading", and the folder is shown when it arrives (`notifyChange`).

## Changes by other clients

rclone's VFS keeps a folder's listing for five minutes (`--dir-cache-time`). Each pass of a network drive folder asks the mounted backend's change log what changed since the previous pass and has the VFS forget those paths (`syncative/mount-poll`, an RPC call of Syncative's in `src/go/rclone/networkdrive.go`), so the mount follows the remote's interval and pause like a synced folder; rclone's own poll timer is off (`PollInterval` 0). Google Drive and Dropbox answer from the fork's change-log calls, Proton (`src/go/proton/rclonefs`) from the volume's event log. That log names a moved file by its new parent only, so the Proton backend remembers where it listed each file once a mount follows the log, and the VFS forgets the folder the file left as well. Nextcloud and ownCloud have no change log, but give a folder a new ETag whenever anything below it changes: the poll reads the mounted folder's ETag and those of its subfolders (`davtags.go`) and follows the changed ones down, one request when nothing changed. Other WebDAV servers have neither and show other clients' changes after the five minutes.

Testing: add a network drive folder in the test instance (with `beta-features` in its data dir), then read and write through the mount and watch the change arrive in a synced folder of the same remote folder. On Android the same works through the Files app: open, copy in, new folder, rename and delete, with a synced folder of the same remote folder to see the result.
